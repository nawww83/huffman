# Huffman — канонический кодек Хаффмана

Компактная библиотека сжатия без потерь (канонический код Хаффмана), утилита
командной строки и измерительный стенд. Зависимостей нет — только стандартная
библиотека, требуется C++20.

Гарантия, на которую опирается всё остальное: `decode(encode(x)) == x` для любых
входных данных, включая пустой вход и алфавит из одного символа.

## Сборка

```sh
cmake -S . -B build
cmake --build build
ctest --test-dir build --output-on-failure
```

По умолчанию собирается `Release`: замеры производительности имеют смысл только
в оптимизированной сборке, поэтому она выбрана вместо «пустого» типа по
умолчанию. Опции CMake:

| Опция | По умолчанию | Что делает |
| --- | --- | --- |
| `HUFFMAN_BUILD_TESTS` | `ON` | собирает `huffman_tests` и регистрирует тест в CTest |
| `HUFFMAN_BUILD_BENCH_TOOLS` | `ON` | собирает `huffman_freq_probe` для `bench/measure.ps1` |

Предупреждения (`-Wall -Wextra -Wpedantic -Wshadow` либо `/W4 /permissive-`)
включаются отдельно для каждой цели, чтобы не навязываться потребителям
библиотеки. Проверено на clang 17 (llvm-mingw), MSVC 19.50 и GCC 11.4: сборки
проходят без единого предупреждения.

Пример явной конфигурации:

```sh
cmake -S . -B build -G Ninja \
      -DCMAKE_BUILD_TYPE=Release \
      -DCMAKE_CXX_COMPILER=clang++
cmake --build build
```

## Командная строка

```
huffman [bench] [опции]        замер пропускной способности (режим по умолчанию)
huffman encode <вход> [выход] [-v]   сжать файл
huffman decode <вход> [выход]        распаковать файл
huffman --help
```

```sh
$ huffman encode data.bin data.huf --verify
data.bin -> data.huf: 400000 -> 324323 bytes (81.0807 %)
round trip verified

$ huffman decode data.huf data.out
data.huf -> data.out: 324323 -> 400000 bytes
```

Если выходной файл не указан, при сжатии используется `<вход>.huf`, при
распаковке — имя входа без расширения. Ключ `-v/--verify` после сжатия
распаковывает результат и сравнивает его с исходными данными, то есть проверяет
круговой обход на реальном файле.

Опции режима `bench`:

| Опция | Смысл |
| --- | --- |
| `--bytes N` | размер блока в байтах (по умолчанию 1048576) |
| `--mb N` | размер блока в МиБ |
| `--iters N` | число измеряемых итераций (по умолчанию 64) |
| `--p P` | фиксированный параметр геометрического распределения |
| `--p-range A B` | параметр выбирается из диапазона (по умолчанию 0.25 0.75) |
| `--seed N` | зерно генератора (по умолчанию 12345) |
| `--p-uniform` | параметр `p` выбирается из `U(0, 1)` — широкий диапазон алфавитов |

Генератор детерминирован: одно и то же зерно даёт одни и те же данные с точностью
до реализации стандартной библиотеки, поэтому замеры воспроизводимы.

## Библиотека

Полный конвейер разбит на шаги, каждый из которых можно протестировать
отдельно:

```cpp
huffman::histogram  freq  = huffman::count_frequencies(input);
huffman::code_table table = huffman::build_code_table(freq);
std::size_t         bits  = huffman::encoded_bits(table, freq);

std::vector<std::uint8_t> payload;
huffman::encode_payload(table, input, bits, payload);

std::vector<std::uint8_t> restored;
huffman::decode_payload(table, payload, input.size(), restored);
```

Основные типы и функции:

- `histogram` — `std::array<std::uint64_t, 256>`, счётчики 64-битные;
- `code_table` — плоские массивы `code[256]` (`uint32_t`) и `len[256]`
  (`uint8_t`, ноль означает «символ отсутствует»), плюс `symbols` и `max_len`;
- `build_code_table()` — дерево на минимальной куче, `O(M log M)`, затем
  канонические коды в порядке `(длина, символ)`; декодер строит таблицу по тому
  же правилу, поэтому стороны не расходятся;
- `encoded_bits()` — два overload'а: по входу и по готовой гистограмме (по
  гистограмме — бесплатно, так как она уже посчитана);
- `encode_payload()` — 4-аргументная версия принимает точное число бит, что
  позволяет писать в заранее выделенный буфер; 3-аргументная считает его сама;
- `compress()` / `decompress()` — самодостаточный контейнер;
- `encode_buffer()` — всё сразу, в одном вызове (его и измеряет стенд);
- `container_header_size(symbols)` — `16 + 2 * symbols` байт.

Особенности, на которые стоит обратить внимание:

- **Вырожденный алфавит поддержан.** Для одного символа длина сообщается как 1
  (чтобы `len != 0` означало «символ присутствует»), но полезных бит не
  пишется — полезная нагрузка пуста, декодер разворачивает `symbol_count` копий.
  Пустой вход также корректен: контейнер содержит только заголовок.
- **Ограничение длины кода.** `max_code_length = 32`. Если дерево оказывается
  глубже, частоты делятся пополам и дерево строится заново, пока ограничение не
  выполнится. Это делает утверждение «код не длиннее 32 бит» инвариантом, а не
  пожеланием: без него «перекошенные» гистограммы (например, числа Фибоначчи в
  счётчиках) дают коды длиной в сотни бит, которые нельзя уложить в `uint32_t`.
- **`decode_payload()` бросает `std::runtime_error`**, если поток не образует
  корректного кодового слова; `decompress()` — если заголовок повреждён.

## Формат контейнера

Все многобайтовые поля — little-endian.

| Смещение | Размер | Поле |
| --- | --- | --- |
| 0 | 4 | сигнатура `"HF1\0"` |
| 4 | 8 | размер исходных данных (`uint64`) |
| 12 | 2 | число присутствующих символов `M` (`uint16`) |
| 14 | 2 | максимальная длина кода (`uint16`) |
| 16 | `2*M` | пары `(байт, длина кода)`, байты по возрастанию |
| `16+2*M` | — | полезная нагрузка: биты MSB-first, последний байт дополнен нулями |

Заголовок занимает `16 + 2*M` байт: для 45 символов это 106 байт. Кодовые
слова в заголовок не пишутся — они восстанавливаются канонически из длин.

## Тесты

```sh
ctest --test-dir build --output-on-failure
# или напрямую
./build/huffman_tests
```

Тесты — один исполняемый файл без внешних фреймворков, с ненулевым кодом
возврата при ошибке. Сейчас это **20 368 проверок, 0 ошибок** (clang 17.0.6 и
GCC 11.4; на другой стандартной библиотеке число может отличаться на единицы,
потому что часть проверок выполняется условно, в зависимости от данных,
которые генерируют распределения из `<random>`).

Покрытие:

- **Побитовый поток**: 400 случайных наборов слов длиной 1…32 бита;
- **Эталонный пример**: `"aaabbc"` → коды `0, 10, 11` → нагрузка `{0x15, 0x80}`;
- **Инварианты таблицы кодов**: префиксная свобода, насыщенность неравенства
  Крафта, код укладывается в свою длину, согласованность `symbols`/`max_len`;
  проверяются для плоских гистограмм всех размеров алфавита от 1 до 256;
- **Краевые распределения**: два символа с равными частотами, один доминирующий
  символ на фоне длинного хвоста, разброс частот в 62 двоичных порядка,
  счётчики на границе `uint64_t`;
- **Ограничение длины**: 60 символов с числами Фибоначчи в счётчиках (дерево
  глубиной 59 сводится к 30);
- **Вырожденный алфавит**: пустой вход и один символ (полезная нагрузка пуста);
- **Размеры и выравнивание**: размеры 0…4096, включая 0/1/2/3/7/8/9/15/16/17/31/
  32/33, плюс проверка, что добивочные биты нулевые, а размер контейнера равен
  `заголовок + payload`;
- **Согласованность двух overload'ов** `encoded_bits()`, а также согласованность
  полезной нагрузки и полного контейнера — на каждом прогоне;
- **Случайный фаззинг**: 400 случайных входов девяти «форм» (равномерное,
  узкий алфавит, геометрическое, доминирующий символ, степенной хвост,
  периодический, константа, пустой) и 400 случайных гистограмм напрямую в
  построитель дерева;
- **Отказ на повреждённых данных**: обрезанный заголовок, обрезанная таблица
  символов, испорченная сигнатура, некорректные счётчик символов, длина кода и
  `max_len`.

Все проверки идут через одну функцию `check_round_trip()`, которая на каждом
наборе данных прогоняет круговой обход, сверяет число бит, нулевую добивку,
размер контейнера и детерминированность результата.

## Производительность

Замер: блок 1 МиБ, 64 итерации, источник `--p-uniform` (геометрическое
распределение, широкий алфавит), затем «лучшее из 25» на последнем входе.
Полный цикл (`encode_buffer()`: гистограмма + модель + полезная нагрузка) —
**560…615 МБ/с** (медиана по итерациям) на Core i7-12700 при привязке к одному
ядру; при `--seed 12345` «лучшее из 25» — 600…635 МБ/с.

Коэффициент сжатия на таком источнике зависит от того, какое `p` выпало на
итерациях: при `--seed 12345` последний вход — 27 символов и 325220 байт из
1048576 (31 %), при `--seed 3` — 44 символа и 424325 байт (40.5 %), а по сетке
`p` от 0.0001 до 0.9 — от 93 % (при `p` около 0.01) до 14 % (при `p` = 0.9). На
реальном файле со смещённым распределением байтов (`data.bin`, 400 КБ) — 81 %.

Разбивка по фазам (1 МиБ, `--seed 12345`; кодирование — лучшее из 5,
декодирование — из 25):

| Фаза | Время | Пропускная способность |
| --- | --- | --- |
| гистограмма | 0.65 мс | 1630 МБ/с |
| построение модели | 0.004 мс | — |
| полезная нагрузка | 1.05 мс | 1000 МБ/с |
| декодирование нагрузки | 3.26 мс | 321 МБ/с |

Отношение между фазами устойчиво: построение дерева практически бесплатно, а
время делится между подсчётом частот и упаковкой битов, причём упаковка примерно
в 1.6 раза дороже подсчёта, потому что на каждый байт приходится переменное
число бит.

Декодирование медленнее кодирования: на том же блоке — около **320 МБ/с**, то
есть втрое медленнее упаковки. Полный `decompress()` (заголовок + перестроение
модели + та же нагрузка) даёт ту же цифру — заголовок и модель занимают доли
процента времени. По сетке `p` от 0.0001 до 0.9 скорость декодирования меняется
от 315 до 470 МБ/с: медленнее всего при `p` около 0.001–0.003, где алфавит
максимален и коды длиннее.

Абсолютные МБ/с сильно зависят от текущей частоты ядра: на одном и том же входе
в разных запусках получалось от 430 до 760 МБ/с (min…max по 64 итерациям).
Поэтому одиночный замер сам по себе мало что значит, а сравнивать имеет смысл
только две сборки, измеренные подряд на одном ядре с нормировкой по частоте —
методика описана ниже. Цифры выше получены командой
`taskset -c 3 ./build/huffman bench --p-uniform --seed 12345` на Linux.

## Как воспроизвести замеры

Абсолютные МБ/с не переносятся между машинами: число зависит от ядра, от
частоты под turbo boost и температуры, а два замера, сделанные с разницей в
минуту, расходятся на проценты. `bench/measure.ps1` делает сравнение двух
сборок корректным:

1. **Привязка к ядру.** Каждый процесс получает `ProcessorAffinity` одного
   физического ядра и класс приоритета `High`. Заодно исключается миграция
   между ядрами с разной частотой.
2. **Учёт turbo boost.** Перед и после каждого замера запускается
   `bench/freq_probe.cpp` — длинная цепочка зависимых операций, скорость
   которой пропорциональна текущей частоте ядра (выводится `ops_per_ns`).
   Пропускная способность домножается на отношение опорной частоты к измеренной.
   В качестве опоры берётся максимальная наблюдённая частота (полный turbo).
3. **Чередование.** A и B измеряются в одном раунде подряд, так что обе
   программы видят одинаковое тепловое состояние; раундов несколько.

Типичные применения: сравнить два компилятора, `-O2` против `-O3`, или две
редакции горячего кода.

```powershell
cmake --build build
.\bench\measure.ps1 `
    -A .\build\huffman.exe `
    -B .\build-o2\huffman.exe `
    -ArgsA bench,'--p-uniform','--seed','12345' `
    -ArgsB bench,'--p-uniform','--seed','12345' `
    -Rounds 8
```

Скрипт сам находит `huffman_freq_probe.exe` в `build/` (или принимает `-Probe`),
поддерживает `-Core` и `-PatternA/-PatternB` для разбора вывода сравниваемой
программы. Требуется Windows с PowerShell; на Linux достаточно
`taskset -c 2` и того же зонда.

## Замечания по реализации

- **Гистограмма.** Один проход по входу, 64-битные счётчики. Никакого
  масштабирования и повторного прохода по данным: модель строится по точным
  частотам, поэтому результат не зависит от длины блока.
- **Канонические коды.** Длины назначаются в порядке `(длина, символ)`, и
  декодер восстанавливает коды ровно по тому же правилу. Поэтому в контейнере
  достаточно хранить длины — по два байта на символ, — а не сами кодовые слова.
- **Дерево.** Минимальная куча с ключом `(частота, индекс узла)`; индекс входит
  в ключ, чтобы при равных частотах результат был детерминирован. Сложность
  `O(M log M)`, где `M` — размер алфавита.
- **Код в плоских массивах.** `code[256]`/`len[256]` вместо структур на символ:
  горячий цикл читает два линейных массива и ничего не разыменовывает на каждой
  итерации.
- **Запись битов через сырой указатель.** Буфер имеет точный размер
  (`payload_size(bit_count)`), поэтому у писателя нет ни проверок ёмкости, ни
  учёта состояния вектора. Вариант, построенный на `std::vector`, оказался в
  3.4 раза медленнее: аккумулятор выносился на стек, а сброс слова превращался
  в настоящий вызов функции вместо инлайна.
- **Порядок бит фиксирован вручную.** 32-битное слово разбирается на байты
  явными сдвигами, а не приведением указателя, поэтому результат не зависит от
  порядка байтов на хосте.
- **Ограничение длины кода** устроено как цикл «построить дерево → если слишком
  глубоко, уменьшить частоты вдвое → повторить». Цикл сходится, потому что при
  всех единицах дерево сбалансировано и ограничение выполняется заведомо.
- **Два overload'а `encoded_bits()`** должны давать одно и то же число; это
  отдельно проверяется тестами, потому что здесь легко разойтись на вырожденном
  алфавите.
- **Декодер: корневая таблица.** Одноуровневая таблица на `min(max_len, 12)` бит
  (не больше 8 КиБ), запись упакована в `uint16_t` как `(длина << 8) | символ`.
  В отличие от «полной» таблицы на 32 бита, 12-битный корень остаётся в кэше, а
  коды длиннее 12 бит — редкость: на них (как и на невалидных префиксах) работает
  побитовый `canonical_walk`, идущий по тому же каноническому порядку и
  продолжающий с текущей позиции. Поэтому таблица не «съедает» невалидный
  префикс: повреждённая нагрузка по-прежнему отвергается.
- **Декодер: скользящее 64-битное окно.** Вместо пересчёта абсолютного
  `bit_offset` на каждый символ окно пополняется невыровненной 8-байтовой
  загрузкой. После пополнения в окне всегда не меньше 57 бит, что покрывает
  самый длинный код (32 бита) вместе с индексом таблицы (12). Хвост меньше 8
  байт добивается нулями побайтово, так что отдельной ветки на конец потока нет.
- **Декодер: два символа за проход.** Если после первого символа в окне осталось
  не меньше 12 бит, второй берётся из той же таблицы без повторной загрузки и
  без новой итерации цикла.

## Проверенные и отвергнутые оптимизации

- **Отдельная таблица пар символов** (индекс — два декодируемых символа сразу)
  была реализована и измерена: **0.87–0.91×**, то есть стабильно медленнее. Причина — построение таблицы на
  каждый блок и промахи кэша при её обходе перекрывают экономию на битовых
  операциях. Не используется; в коде её нет. Это не то же самое, что нынешние
  «два символа за проход»: там два символа берутся из одной и той же корневой
  таблицы, а не из таблицы с индексом по паре.
- **Расширение кода до 64 бит** вместо ограничения длины: потребовало бы другого
  формата заголовка и более дорогого горячего цикла ради случая, который на
  реальных данных практически не встречается. Выбрано деление частот.
